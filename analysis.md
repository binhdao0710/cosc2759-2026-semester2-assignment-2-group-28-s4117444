# Analysis

## 1. Problem Analysis

Yeetcode Inc.'s Posts application was being deployed to production manually,
which is slow and prone to human error. The task was to design and build a
fully automated deployment pipeline, covering both infrastructure provisioning
and application deployment, so that the frontend, backend, and database services
can be reliably stood up on AWS from a single push to GitHub.

The core challenges were:

- Provisioning AWS infrastructure (EC2 instances, security groups, load
  balancers) in a repeatable, and automated way.
- Installing Docker and running the correct containers with the correct
  configuration across multiple EC2 instances, without manual SSH steps
- Restricting network access so that each service can only be reached by
  the required serivces.
- Making the frontend and backend resilient by running multiple instances
  of each and configure load balancers for both ends.
- Automating the entire deployment process with a CD pipeline, ensuring that
  no AWS credentials are ever hardcoded or committed to the repository
- Ensuring Terraform's state is preserved across pipeline runs.

## 2. Sections Completed

This submission implements **Sections A, B, C, and D**.

- **Section A**: Backend and Database containers deployed and correctly
  configured, with a bash script (`deploy.sh`) that fully automates the
  deployment.
- **Section B**: Frontend container added and publicly reachable,
  successfully communicating with the Backend.
- **Section C**: Frontend, Backend, and Database split across separate EC2
  instances, each with its own security group, with a GitHub Actions
  workflow that fully automates provisioning and deployment on pushes to
  `main`, with no AWS credentials hardcoded or committed.
- **Section D**: Frontend and Backend each deployed across two EC2
  instances, with requests to each load balanced by an Application Load
  Balancer. Terraform state is stored remotely in an S3 bucket rather than
  on the machine running Terraform.

## 3. Solution Design and Justification

### 3.1 Terraform

Five EC2 instances are provisioned in the AWS Learner Lab's default VPC: one
database instance, two backend instances, and two frontend instances. An
Ubuntu AMI is resolved dynamically via a `data "aws_ami"` lookup rather than
a hardcoded AMI ID, since AMI IDs are region-specific and change over time.

Security groups follow the principle of least privilege, with a separate
group for each tier:

- **Database SG**: Allows inbound PostgreSQL (5432) only from the Backend
  security group, referenced by the security group ID, and SSH (22) from
  anywhere for Ansible to configure the instance. The database is not reachable
  at port 5432 from the public internet under any circumstance.
- **Backend SG**: Allows inbound traffic on port 8080 only from the Backend
  ALB's security group, along with SSH(22).
- **Frontend SG**: Allows inbound traffic on port 8081 only from the
  Frontend ALB's security group, along with SSH(22).
- **ALB security groups**: The load balancer's security group accepts
  public HTTP traffic on port 80 from anywhere.

The backend and frontend EC2 instances are not directly reachable from the
public internet, and all traffic to them must be forwarded through the load
balancer.

SSH is opened broadly on every instance as it is required for Ansible, and
therefore is necessary as part of the CD pipeline.

Two Application Load Balancers were created for the frontend and the backend,
each with its own listener (port 80) and target group. Every instances are
attached to their respective groups with `aws_lb_target_group_attachment`.

An SSH key pair is generated by Terraform itself (`tls_private_key` +
`aws_key_pair`), so the pipeline requires no manual setup steps.

Terraform's state is stored in an S3 bucket rather than on the machine
running Terraform. This was necessary because the GitHub Actions pipeline
runs on a fresh virtual machine every run. The state file ensures no conflict happens
when the infrastructure is provisioned. It also keeps the state file out of the Git
repository entirely, which matters because Terraform state can contain sensitive
values, such as the private key generated for the EC2 key pair.

### 3.2 Ansible

Ansible installs Docker on each of the five instances and starts the
appropriate container, using the `community.docker.docker_container`
module. The inventory is generated dynamically by `deploy.sh` from
Terraform's outputs (IPs and ALB DNS names).

Initially, containers rely on Docker's internal container-name resolution.
But this only worked when they shared a host. When the backend, frontend, and
database became separated on different EC2 instances, their connection was
configured via the security groups in Terraform. Therefore, the playbook is
condfigured to setup Docker and the Python SDK on multiple instances instaed of
one.

`image_name_mismatch: recreate` is set on each container task so the
playbook is self-healing: If a container with a given name already exists
but doesn't match the desired image Ansible recreates it rather than erroring
out. This matters particularly for the unattended GitHub Actions pipeline, where
no manaul intervention is available.

### 3.3 Automated Deployment

As described in the README.md file, `deploy.sh` orchestrates the full pipeline:
it checks that Terraform and Ansible are available, runs Terraform, waits for SSH
to become available on every instance, builds the Ansible inventory from Terraform's
outputs, and runs the playbook.

Credentials are never stored in the repository. Initially, this was enforced by
having AWS credentials and database credentials as pre-exported environment
variables. The database credentials prompted interactively otherwise if not present,
with silent input for the password.

The GitHub Actions workflow (`cd-pipeline.yaml`) runs this same script on a fresh
Ubuntu runner, triggered only on pushes to the `main` branch, as required. Terraform
and Ansible are installed fresh on the runner each time it fires, since nothing
persists between runs. All five credentials are injected via GitHub Actions Secrets,
which are encrypted at rest and only exposed as environment variables at runtime.

## 4. Known Limitations

- AWS Academy Learner Lab issues temporary credentials, including a session
  token, that expire after a few hours. This means the GitHub Actions
  secrets must be refreshed manually before a deployment run.
- The S3 bucket used for Terraform's remote state must exist before
  `terraform init` can run against it. This bucket was created manually, outside of
  Terraform, so it is not managed in code, and the infrastructure cannot be rebuilt
  entirely from the repository without this one-off setup step.
